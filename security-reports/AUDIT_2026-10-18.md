# WEB-KPAH Security audit — 2026-10-18

## Evidence scope
Source: GitHub `thachdeptrai/web-kpah`, branch `main`. The repository tree returned **321 entries** and was not truncated. Examined routing, server security policy, auth/account/reset, administrator guards, giftcode administration, card/payOS callback, VNĐ wallet, Point ledger, notification ownership and critical operational scripts. This was a **source-tracing and focused CI audit**; it is not an all-endpoint dynamic penetration test.

No requests were sent to the production application. No production database, account, token, checkout, callback, giftcode or balance was changed. `src/` does not exist in the GitHub repository tree: there is a separately versioned `game-server-patch/`; the historical local Java archive is not a confirmed deployed game binary.

## Verified and patched

| ID | Severity | Finding | Impact | Patch on main | Validation |
| --- | --- | --- | --- | --- | --- |
| AUTH-2026-01 | Medium | Player login rate limiting applied exclusively to the concatenated `source IP + username` pair. | One network source could spread attempts across many account names without exhausting a network-wide budget. | `app/pages/login.php`: independent 80/15m per-IP, 20/15m per-username, existing 8/15m per pair; backend fails closed when rate-limit storage fails. Commit `2b0ad4d4`. | PHP syntax and Vibe CI passed; `tests/security_auth_url_smoke.php` checks all three budgets and conjunction, security CI passed. |
| URL-2026-01 | Medium | The shared `kp_safe_url()` rejected `//external` but accepted leading backslashes, which WHATWG URL resolution may interpret as external authority. | Malicious link values from configuration/content could redirect a visitor off site even when they look like relative links. | `app/includes/security.php`: reject backslashes and control bytes before accepting URLs. Commit `79bf122e`. | `tests/security_auth_url_smoke.php` checks valid relative/HTTPS links and malicious protocol-relative/backslash/control/scheme values; security CI passed. |

Both fixes preserve PHP routes and the database/payment schemas. They do not modify money balances, item grants or serialized game items.

## Current controls observed, not blanket assurances
- Session IDs regenerated after login; admin and player sessions use distinct cookie names. Cookies use HttpOnly and Lax with Secure on HTTPS; idle-timeout and active-ban checks exist.
- CSRF tokens used on sensitive browser writes, centralized admin MFA/role guard and owner checks on user queries.
- PDO statements bind user values, while existing constant SQL query strings remain. No confirmed SQL injection was established in sampled PHP endpoints.
- payOS callback checks HMAC and obtains authoritative payment state through provider interaction; card callback checks signature and own stored fingerprint.
- VNĐ wallet uses named lock and compare-and-swap updates; Point wallet uses InnoDB transaction and ledger idempotency; MyISAM game tables remain non-transactional.
- Apache `.htaccess` denies private directories and limits access to numeric `res/icon/*.png` when Apache rewrite config is actually enforced.
- Vibe Check only probes its **local fixture**. It is not a live production or staging security test.

## Important conditional and unverified risks

| Severity if exposed | Risk | Status / required action |
| --- | --- | --- |
| High (conditional) | `security.trusted_ip_header` accepts a configured forwarded header without a code-level proxy IP allowlist. A directly reachable origin would let clients spoof source address, weaken IP rate limiting and potentially admin IP allowlist. | **Not changed automatically**: verify Cloudflare/origin firewall trust topology and choose an explicit trusted proxy network design before altering production networking. Default config leaves the header unset. |
| High (conditional) | Legacy double-SHA1-compatible passwords remain because the Java game login uses the same hash. | **Unpatched by design**: migrate the game server and website together using a reviewed credential upgrade, not unilateral bcrypt conversion. |
| Critical if exposed / activated | The independently supplied Java source previously showed unsafe dynamic SQL in admin tools and an optional insecure listener. | **Not tested on deployed server**. Review and patch the actual deployed Java project before enabling optional ports. |
| High for financial consistency | Wallet/grant actions write to legacy MyISAM tables and file journals; exact-once delivery under OS crash, two VPS workers, or provider replay needs staging tests. | **Not proven** with real integration tests. Preserve reconciliation records and use dedicated staging payment credentials. |
| Medium | `kp_topup_recent()` scans filesystem history; maintaining performance and exact deduplication at large scale requires capacity testing. | **Not changed**, because changing settlement or historical record format without staging is unsafe. |
| Medium | Proxy TLS termination and Apache `AllowOverride` behavior determine whether security headers, cookie flags and file access rules work as expected. | **Deployment verification needed** with authorized access. |

## Required manual staging plan
1. Establish a separate sanitized MySQL database, isolated game test process, writable protected storage and payment sandbox credentials.
2. Test role matrix: unauthenticated, normal, blocked user, key and admin against each private route (including direct API POSTs).
3. Test parallel bank webhook notifications, card retries and user/administrator duplicate Point redeems, verifying exact final balances and ledgers; inject a staging-only simulated crash between debit and grant to check reconciliation.
4. Validate giftcode item tokens against the deployed Java parser and item option limits, especially before enabling `KPAH_GIFTCODE_DBO_ENABLED`.
5. Run ZAP/Nuclei/Strix **only against authorized staging** with bounded traffic and documented test accounts; check false positives manually.
6. Verify external `storage/` denial, absent web-executable uploads, Cloudflare-to-origin restrictions and header propagation.

### Future review checklist
Re-check sensitive backend endpoints after every payment, wallet, giftcode, item, auth or role change. Record new findings with file/line, exploit preconditions, test proof, patch SHA and remaining limitations. Do not approve changes based only on Vibe Check's local headers/CORS scan.

**Conclusion:** Two independently reproduced/traceable source-level weaknesses were patched and backed by regression CI. No evidence supports a claim of complete site security or safe production payout concurrency without staging tests.
